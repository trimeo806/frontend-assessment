Phase-by-Phase Breakdown

1

Brainstorm

Research

Understand exactly what needs to be built before any research begins.

  • Read the assessment in full; annotate every requirement
  • Decompose into deliverables: 4 screens, Duffel API, docs, deployment
  • Identify unknowns: endpoints needed, state that persists across screens
  • Define "done" for each screen
Output: Requirements checklist · scope decisions
2

Competitor Research

Research

Understand how production OTAs solve the same UX problems before designing anything.

  • Tested 7 platforms: Google Flights, Skyscanner, Expedia, AirAsia, Booking.com, Kayak, Trip.com
  • Measured load time, booking time, UX score, design style
  • Identified patterns to adopt and patterns to avoid
Output: 4-research-ui-ux.md · competitor-analysis.md
3

Tech Stack Research

Research

Select libraries with clear rationale, not defaults.

  • Zustand over Redux — 2 KB vs 25 KB, no boilerplate
  • React Hook Form + Zod — no re-render per keystroke, runtime + static types
  • shadcn/ui — Radix UI a11y primitives, no vendor lock-in
  • Raw fetch — 98% smaller than SDK; readable and debuggable
Output: 3-research-overview-frontend.md
4

API & Library Research

Research

Understand the Duffel API deeply before writing any integration code.

  • Live-tested all 6 Duffel endpoints in the booking flow
  • Mapped TypeScript interfaces from live response shapes
  • Discovered: round-trip returns 1,638 results inline → return_offers=false required
  • Verified passengerIds[] must be stored verbatim in the order payload
Output: 2-duffel-api-exploration.md
5

Plan

Planning

Produce detailed implementation plans before writing any production code.

  • 00-architecture.md — component hierarchy, rendering strategy
  • 01-tailwind-config.md — design tokens, color system
  • 04-data-layer.md — Server Actions, Route Handlers
  • 05-route-guards-persistence.md — Zustand store shape, session persistence
  • + 8 more plan files covering forms, layout, animations, responsive
Output: 12 implementation plan files
6

Architecture Gate

Planning

Lock architecture before implementation to prevent expensive structural rework.

  • frontend-architect agent reviewed component hierarchy and rendering strategy
  • TanStack Query removed — Server Actions made it redundant
  • useHydrated() pattern added — SSR hydration risk flagged
  • Server Actions for mutations; Route Handlers for client fetching
Output: Final 00-architecture.md (locked)
7

Implement

Build

Build all 4 screens following the locked architecture.

  • Foundation: Tailwind tokens, shadcn/ui, Zustand store, duffelFetch, i18n
  • F1 Search: AirportCombobox, DateRangePicker, PassengerSelector, SearchForm
  • F2 Results: ResultsList, FlightCard, FilterPanel, SortBar, useFilteredOffers
  • F3 Passengers: PassengerForm, BookingSummary, OfferExpiryGuard, createOrder()
  • F4 Confirmation: ConfirmationCard, Server Component direct Duffel fetch
Output: 40+ components · 3 Server Actions · 2 Route Handlers
8

Code Review

Build

Catch issues before testing — TypeScript, accessibility, code quality.

  • TypeScript strictness: no any, correct Duffel type mappings
  • Accessibility: ARIA labels, keyboard nav, focus management, color contrast
  • Code quality: no dead code, consistent naming, no prop drilling, server-only boundaries
Output: Issues list → all fixed before testing
9

Test & Fix

Verify & Ship

Verify the end-to-end booking flow in a real browser with live Duffel test API calls.

  • Full flow: Search → select → passenger form → confirm → confirmation
  • Edge cases: offer expiry, price change, back-navigation after booking
  • Round-trip: outbound + return displayed correctly
  • Mobile, i18n, filter drawer verified
Output: 3 bugs found and fixed
10

Deploy

Verify & Ship

Verified working deployment on Vercel.

  • Connected GitHub repository to Vercel
  • Set DUFFEL_API_KEY in Vercel environment variables
  • Triggered deployment via git push origin master
  • Verified live URL end-to-end: search → booking confirmation
Output: flight-explorer-twenty-six.vercel.app/en

Key Learnings

01

Research before planning, plan before coding. The 12 implementation plan files took ~20% of total time but prevented multiple expensive architectural decisions from being made incorrectly mid-implementation.

02

Architecture gate catches expensive issues early. The useHydrated() pattern and the removal of TanStack Query were both caught at the architecture gate, not during implementation.

03

Live API testing is non-negotiable. The return_offers=false requirement was only discoverable through live testing, not documentation. TypeScript types were more accurate from live responses than from docs.

04

Competitor research influences concrete decisions. The choice of Skyscanner's color system (#0770E3), 52px input sizing, and filter panel placement came directly from 7-OTA research, not from default choices.
